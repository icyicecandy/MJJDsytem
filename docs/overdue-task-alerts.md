# Overdue task alerts

Completed verification: September 20, 2026.

## Behavior

- Active administrators receive overdue installation and ticket alerts for the team. Only the assigned, active technician receives the corresponding technician alert. Customers and unrelated technicians do not receive these staff alerts.
- An appointment becomes overdue when its scheduled one-hour slot ends and its task remains active. Checks are scheduled every five minutes in the application timezone. Delivery may therefore occur up to five minutes after slot end while the scheduler is running.
- Alerts appear in the existing notification bell and Notifications page. Each includes the task reference, appointment date/time, timezone, and a link to the authorized task page.
- Technicians are prompted to update progress or contact an administrator about rescheduling. Administrators are prompted to review progress and arrange rescheduling if needed. Alerts do not automatically change task status, technician assignment, or appointment times.
- A persistent delivery marker prevents repeated alerts for the same task, appointment, assignment, and recipient, even if a notification is read or deleted. A changed appointment or assignment can produce a new alert when overdue.
- Completed, activated, resolved, closed, cancelled, and pending-review work is excluded. Pending customer rescheduling or application cancellation pauses installation overdue alerts; existing review notifications remain responsible for those cases.
- Tasks without a complete appointment have no inferred deadline and are skipped. This is appointment overdue detection, not a general ticket response-time SLA or recurring escalation policy.
- Notifications and their delivery markers commit together under existing workflow locks. A failed database write rolls back the marker so a later scheduled check can retry. Concurrent checks serialize on the task's workflow locks.

## Running automatically

The Laravel schedule contains `tasks:alert-overdue` every five minutes with overlapping scheduler runs prevented. These are database-backed in-app notifications; no email/SMS provider or queue worker is needed for this feature.

The local migration was applied and a dry run succeeded. No Windows scheduled task for this project was found, and this implementation does not install an operating-system task or leave a temporary background process running.

For local development, keep this command running in a separate terminal from the project directory:

```powershell
php artisan schedule:work
```

For deployment, configure the hosting scheduler to execute `php artisan schedule:run` from the deployed project directory every minute. Use the correct PHP executable and application account. The server must be running and able to reach its database. The same Laravel scheduler also runs the existing daily expired-draft cleanup.

Preview without creating notifications:

```powershell
php artisan tasks:alert-overdue --dry-run
```

Run a single delivery check when intended:

```powershell
php artisan tasks:alert-overdue
```

Alerts already delivered remain historical notifications if a task later completes or moves to a different date. Open the linked task for its current state; normal role/assignment authorization still applies.

Original source checkpoint: `.checkpoints/before-overdue-alerts-20260916.zip`. Do not restore the entire archive over later user changes. To disable automatic overdue alerts, stop the relevant scheduler during the change and remove only the `tasks:alert-overdue` schedule entry; preserve the draft cleanup schedule and other work.

For a full feature rollback, first back up the current database and source, confirm this migration is still the latest migration, and remove the overdue command/service/test files along with their schedule entry. Roll back only this migration:

```powershell
php artisan migrate:rollback --path=database/migrations/2026_09_16_000004_create_overdue_alert_deliveries_table.php --step=1 --force
```

Then remove the migration file. This drops only the delivery-marker table; existing task records and notification history remain. Removing the markers means a future reinstallation can alert again about existing overdue appointments. Preserve unrelated edits and later migrations.
